1. EXECUTIVE SUMMARY (कार्यकारी सारांश)
====================================================================================================
Mahirash ek high-performance, modern Luxury E-Commerce Web Application hai jo bespoke artisanal perfumes,
rare Cambodian oud extraits aur luxury fragrance discovery sets sell karne ke liye design kiya gaya hai.

Architecture Pattern:
- Frontend: Single Page Application (SPA) based on React 19 + Vite 8.
- Backend: Serverless Microservices / API Gateway based on Node.js running on Vercel Functions.
- Database & Identity: Google Cloud Firestore (NoSQL Document DB) + Firebase Authentication.
- Assets CDN: Cloudinary for optimized image transformations and video streaming.
- Payment Gateway: Razorpay (Credit/Debit Card, UPI, NetBanking) + Cash on Delivery (COD).
- Logistics & Fulfillment: Shiprocket API + Delhivery Express B2C API for nationwide automated shipping.
- Artificial Intelligence: Google Gemini AI (gemini-1.5-flash) for virtual fragrance concierge.

Project ka primary objective luxury brand aesthetics (smooth animations, 3D interactive elements,
responsive design) ke sath enterprise-grade e-commerce reliability provide karna hai.

5. REQUEST HANDLING & ROUTING MECHANISM (रिक्वेस्ट कैसे प्रोसेस होती है)
====================================================================================================

5.1 FRONTEND CLIENT ROUTING (React Router DOM v7):
--------------------------------------------------
- Entry Point: 'src/main.jsx' mounts <App /> wrapped in AuthProvider, CustomerAuthProvider, StoreProvider.
- Path Rewrites: 'vercel.json' specifies that any non-API path '/(.*)' routes to '/index.html' (SPA).
- Code Splitting: All major views (Admin, Shop, Checkout, ProductDetail, Orders, TrackOrder) are
  wrapped in React.lazy() and Suspense with a luxury RouteLoader to minimize initial bundle size.

5.2 BACKEND SERVERLESS API GATEWAY (Vercel Functions):
------------------------------------------------------
All incoming backend calls target '/api/*'.
In 'vercel.json', rewrites are configured as:
  { "source": "/api/(.*)", "destination": "/api/index.js?__route=$1" }

Request Processing Steps in 'api/index.js':
  Step 1: Injects uniform response helpers (.status(), .json(), .send()) if running on raw Node server.
  Step 2: Parses URL search query parameters into 'req.query'.
  Step 3: Asynchronously reads and decodes request body (supports JSON strings and raw readable streams).
  Step 4: Normalizes route candidate from req.query.__route or x-matched-path headers (strips .js, slashes).
  Step 5: Health Check: Requests to '/api' or '/api/health' return 200 OK operational status.
  Step 6: Route Lookup: Looks up handler in ROUTE_HANDLERS dictionary:
          - /api/send-otp                 -> api/_handlers/send-otp.js
          - /api/verify-otp               -> api/_handlers/verify-otp.js
          - /api/deduct-stock             -> api/_handlers/deduct-stock.js
          - /api/get-orders               -> api/_handlers/get-orders.js
          - /api/admin-order-status       -> api/_handlers/admin-order-status.js
          - /api/shipping-create-shipment -> api/_handlers/shipping-create-shipment.js
          - /api/shipping-assign-courier  -> api/_handlers/shipping-assign-courier.js
          - /api/shipping-serviceability  -> api/_handlers/shipping-serviceability.js
          - /api/shipping-track           -> api/_handlers/shipping-track.js
          - /api/delhivery/serviceability -> api/_handlers/delhivery-serviceability.js
          - /api/webhooks/shipping        -> api/_handlers/webhooks-shipping.js
          - /api/send-order-email         -> api/_handlers/send-order-email.js
          - /api/link-guest-orders        -> api/_handlers/link-guest-orders.js
  Step 7: Execution & Error Boundary: Executes target handler inside a master try/catch block.
          Unhandled crashes return a sanitized JSON error response with code 500.

6.1 PRODUCT BROWSING & DYNAMIC CATALOG FLOW:
--------------------------------------------
[User visits /shop or /product/:id]

             to compute real-time delivery TAT from Indore hub (452001).

6.2 AUTHENTICATION & IDENTITY FLOW (DUAL AUTH SYSTEM):
------------------------------------------------------
The project uses a dual-layer authentication model:
A. Administrators:
   - Email/password authentication via Firebase Auth ('signInWithEmailAndPassword').
   - Access verified against hardcoded SuperAdmin emails in 'firestore.rules'.
B. Customers (Passwordless OTP System):
   1. User enters Email in Login/Checkout modal -> calls 'POST /api/send-otp'.
   2. Backend checks 45-second cooldown and email format.
   3. Backend generates 6-digit random number via 'crypto.randomInt(100000, 1000000)'.
   4. Generates HMAC-SHA256 hash using secret server salt:
      hashedOtp = HMAC_SHA256(cleanEmail + ":" + otp, OTP_SALT)
   5. Stores record in memory with 10-minute expiry and 5-attempt limit.
   6. Nodemailer sends luxury HTML email containing the OTP.
   7. Customer enters 6 digits -> calls 'POST /api/verify-otp'.
   8. Backend verifies hash using 'crypto.timingSafeEqual' (prevents timing attacks).
   9. On success: OTP is immediately deleted to prevent replay attacks.
  10. Backend creates Firebase Custom Token (RS256 JWT) or verified identity bridge.
  11. Frontend calls 'signInWithCustomToken(auth, customToken)' to establish Firebase Auth session.
  12. Backend automatically triggers '/api/link-guest-orders' to associate past guest orders.

6.3 CART & WISHLIST REALTIME SYNCHRONIZATION FLOW:
--------------------------------------------------
Managed centrally by 'src/components/StoreProvider.jsx':
- Guest Users:
  * Cart and Wishlist stored in browser 'localStorage' ('guest_cart', 'guest_wishlist').
- Logged-in Users:
  * Immediate local cache load for zero UI lag ('user_cart_<uid>').
  * Cloud sync with Firestore document 'users/{uid}'.
  * Realtime listener ('onSnapshot') keeps cart in sync across multiple browser tabs or devices.
  * Auto-Merge: When a guest logs in, unauthenticated cart items are automatically merged into
    the cloud account without duplicating existing items.

6.5 INVENTORY & STOCK MANAGEMENT FLOW:
--------------------------------------
Managed by 'api/_lib/stockManager.js':
- Supports multi-variant sizes (e.g., 50ml, 100ml, Discovery Vials).
- Deducts purchased quantity from matching size variant in 'size_prices' array.
- Recalculates total product stock = sum of variant stocks.
- Automatically updates 'stock_status':
  * Total Stock == 0  --> "Out of Stock"
  * Total Stock <= 5  --> "Low Stock"
  * Total Stock > 5   --> "In Stock"

6.6 LOGISTICS, COURIER DISPATCH & REALTIME TRACKING FLOW:
---------------------------------------------------------
1. Shipment Creation:
   - In Admin Panel (/admin -> OrdersTable), Admin clicks "Create Shipment".
   - Calls 'POST /api/shipping-create-shipment'.
   - Shiprocket API receives package dimensions, weight, customer address.
   - Returns 'shipment_id' and 'awb_code'. Order status set to "Ready to Ship".
2. Courier Pickup:
   - Admin clicks "Assign Courier / Schedule Pickup".
   - Calls 'POST /api/shipping-assign-courier' and 'POST /api/shipping-request-pickup'.
3. Realtime Webhooks:
   - As the courier picks up, transports, and delivers the package, Shiprocket sends webhooks
     to 'POST /api/webhooks/shipping'.
   - Webhook handler verifies security token, validates status progression using rank hierarchy,
     and updates Firestore order document ('shipmentStatus', 'fulfilmentStatus', 'activityLog').
4. Customer Tracking:
   - Customer enters Order ID or AWB in '/track'.
   - System fetches scans from Firestore, Delhivery API, or Shiprocket API and displays visual timeline.

7. SECURITY AUDIT & RISK ANALYSIS (सुरक्षा विश्लेषण)
====================================================================================================

7.1 SECURITY STRENGTHS (मौजूदा मजबूत पहलू):
-------------------------------------------
1. Cryptographic OTP Verification:
   - OTPs are NEVER saved in plain text. Hashed with server-side secret 'OTP_SALT' using HMAC-SHA256.
   - Verified using 'crypto.timingSafeEqual' to eliminate timing side-channel attacks.
   - Strict 10-minute expiry and maximum 5-attempt brute-force protection.
   - Enforced 45-second cooldown rate limit to prevent email flooding.
   - Instant token invalidation upon verification to prevent replay attacks.
2. Firestore Security Rules Isolation:
   - '_otp_verifications' collection has 'allow read, write: if false' (zero client access).
   - Orders: Customers can ONLY read their own orders ('auth.uid == userId' or 'auth.token.email == customerEmail').
   - Products: Only SuperAdmin can create/delete products. Clients are ONLY allowed to update stock fields
     specifically ('stock', 'stock_status', 'size_prices', 'updatedAt') during checkout.
   - CMS & Site Settings: Strictly restricted to Super Admin emails.
3. Strict Input Sanitization:
   - Phone numbers sanitized to 10 digits; PIN codes validated against Indian 6-digit regex;
     strings sanitized against HTML/XSS injection prior to database entry.

7.2 CRITICAL VULNERABILITIES & TECHNICAL DEBT (कमियां और जोखिम):
----------------------------------------------------------------
[CRITICAL SEVERITY - P0]
1. Environment Variable Prefix Exposure (VITE_* Secrets):
   - Finding: In '.env.example', secrets like 'VITE_RAZORPAY_KEY_SECRET', 'VITE_SHIPROCKET_PASSWORD',
     and 'VITE_EMAILJS_PRIVATE_KEY' are prefixed with 'VITE_'.
   - Risk: Any environment variable with the 'VITE_' prefix is bundled into the client-side JavaScript
     bundle during 'vite build'. Anyone inspecting browser network tabs or bundle scripts could extract them.
   - Remediation: Remove 'VITE_' prefix from all backend secrets in Vercel. Use server-only variables:
     RAZORPAY_KEY_SECRET, SHIPROCKET_PASSWORD, SMTP_PASS, etc.

[HIGH SEVERITY - P1]
2. Client-Side Order Creation & Price Integrity Risk:
   - Finding: In 'Checkout.jsx', orders are written directly to Firestore from the browser using 'addDoc()'.
     Payment verification also occurs primarily on the frontend.
   - Risk: A technically skilled adversary could intercept the network request and alter 'total',
     'couponDiscount', or product prices before writing to Firestore.
   - Remediation: Implement a dedicated backend endpoint 'POST /api/create-order' that recalculates
     order totals server-side based on database product prices, verifies the Razorpay signature
     (crypto.createHmac with razorpay_order_id + payment_id), and saves the order securely.

[MEDIUM SEVERITY - P2]
3. In-Memory OTP Store in Serverless Environment:
   - Finding: 'api/_lib/firebaseAdmin.js' uses 'inMemoryOtpStore = new Map()' for tracking OTPs.
   - Risk: Vercel Functions run across multiple stateless lambdas. If the 'send-otp' request hits
     Instance A, and the subsequent 'verify-otp' request hits Instance B (cold start), the OTP record
     will not exist in Instance B's memory, causing false verification failures.
   - Remediation: Store OTP hashes in Firestore with server timestamps or use an Upstash Redis instance.

[LOW SEVERITY - P3]
4. Hardcoded SuperAdmin Emails:
   - Finding: 'firestore.rules' contains hardcoded email addresses:
     'mahirash9999@gmail.com' and 'admin@mahirash.com'.
   - Risk: Changing admin credentials requires modifying and redeploying Firestore security rules.
   - Remediation: Transition to Firebase Custom Claims (request.auth.token.admin == true).
